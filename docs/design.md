# 设计与取舍

这份文档记录**为什么这么写**，以及旧版本踩过的坑。想改代码之前先看这里。

---

## 0. 「轮」的定义

> 一轮 = 从一条 `user` 消息开始，到下一条 `user` 消息前（不含）为止；
> 末尾未收束的自成一轮；第一条 `user` 之前的 `system`/`tool` 等消息归入其后的第一轮。

代码在 `messages.split_rounds()`。所有压缩切点**只允许落在轮边界上**，
因此不会在一轮中间（比如 `assistant` 的 tool_calls 和它的 `tool` 返回之间）切开，
也就不会产生上游会 400 的孤儿 tool 消息。

所有压缩相关日志都同时带轮次和消息下标区间，方便和 chatbox 里的位置对上：

```
[a1b2c3d4] 增量压缩 seq=3：等效 41320 tokens｜待压 第 41~78 轮（下标 82~156，74 条，约 33900 tokens）｜保留 26 条原文｜共 4 批，本次压 4 批
[a1b2c3d4] 第 1/4 批完成：第 41~52 轮（下标 82~104，22 条）｜输入 9820 tokens → 输出 1140 tokens｜累积摘要 7300 tokens｜模型 primary:deepseek-v4-flash｜已落盘至第 52 轮
```

## 1. 会话状态：为什么换成 checkpoint 链

### 旧版的问题

1. **会话指纹取前 3 条非 system 消息、每条按字节截断 500**。中文 500 字节只有约 166 字，
   还可能截在字符中间。开头几条稍微一改就认不出来，落到"新会话"分支从第 0 条全量重压。
2. **只有单一状态点**（`compressed_upto` + 一条边界消息的哈希）。判断"历史是否变了"靠比长度
   和比一条消息的哈希，任何一次插入/删除/重生成都会误判。
3. 一旦判定历史被编辑或变短，把 `compressed_upto` 和累积摘要**一起清零**——
   上万字的累积摘要直接扔掉，然后几千条消息从头重压。
4. 这一条会连锁触发崩溃：全量重压要 30+ 批串行调用，跑几十分钟，客户端超时重发，
   新请求又从头开始，越堆越多。

### 现在的做法

**滑动 checkpoint 链**（`store.checkpoints` 表）：每个会话保留

- 最近 `checkpoint_keep`（默认 10）个 checkpoint，
- **外加一条永久置顶（`pinned=1`）的最早 checkpoint**——第一次触发压缩时那条。

每个 checkpoint 存：当时的累积摘要全文、压缩位置、轮次、消息条数、
以及**当时整条消息列表的逐条指纹数组**（只存指纹不存原文，4000 条约 78 KB）。

> **配额单位是「一次压缩事件」而不是「一个批次」。**
> 一次事件对应一条 `partial` 记录，期间逐批 `UPDATE` 同一行，事件结束才 `sealed`。
> 如果按批次计配额，一次全量重压的几十次落盘会在单次请求内把窗口里的历史 checkpoint 冲干净。

### 会话匹配（宽松，尽量别误判成新会话）

`locate.candidates()`，三级：

1. **精确哈希**：前 5 条 `user` 消息**全文**（不判断是否合格、不截断）拼接后 sha256。
   命中直接走，覆盖绝大多数请求。
2. **锚点匹配**：从当前 body 取 5 个锚点——第 1、第 2 条合格消息，以及全文 25% / 50% / 75%
   位置往后的第一条合格消息（**合格 = 文本长度 ≥ 20 字**）。在指纹倒排表里查，**不依赖顺序**
   （有些客户端消息顺序会乱）。按命中数计分，**硬性要求 ≥ 2 分**；低于 2 分视为未匹配走新建流程；
   多个会话同分则取最近更新的那个并打 `WARNING`。
3. **旧版指纹**：给从旧 `sessions` 表迁移过来的会话认亲用。

精确哈希命中却对不齐时（极小概率：两个会话的前 5 条 user 消息完全相同），
锚点候选仍然会被依次尝试，而不是直接掉进兜底。

### 分支点定位（`locate.align`）

拿当前请求的指纹数组和 checkpoint 的指纹数组做最长公共前缀比对。遇到不等时**先别急着判分叉**：

- 用 ±4 条小窗口 + **三连比对**探测「客户端在中间插了/删了几条」；
- 命中就修正偏移量继续往下比（`shifts` / `net_offset` 会记进日志），历史本体没变；
- 确实对不上才是真分叉，记下**分叉发生在第几轮 / 哪个下标**。

然后选择 `matched_ref >= compressed_upto` 的**最新** checkpoint —— 也就是"分叉点之前最近的那个"。
它已压缩的那段内容完全没被改动，摘要可以照用。

### 定位失败的兜底（`compress._fallback_path`）

极端情况：用户从早期消息改起，对应的 checkpoint 早已滑出窗口，连置顶的最早 checkpoint
的已压缩区都被波及。这时：

- 摘要取**置顶的最早那条 checkpoint**；
- 原文只保留 `keep_recent_tokens` 对应的最近若干轮，之前所有轮次**标记为已压缩**（不再摘要）；
- 注入的摘要末尾追加 `prompts.fallback_notice`，显式告诉主模型：
  用户可能从早期消息创建了分支，摘要与原文衔接处可能重叠或跳跃，**冲突以原文为准**。

这条路径每次触发都 `WARNING` + 计数，在 `/health` 的 `fallback_activations` 里暴露。
**它频繁触发说明上面的定位逻辑有 bug，不该指望兜底扛。**

## 2. 压缩流程的失败恢复

### 旧版的问题

几千条消息全量重压要 30+ 批串行调用摘要模型。**任意一批失败就 `return messages` 整体放弃**，
落盘只在全部批次成功后执行一次——前面几十次调用的成果全丢，`compressed_upto` 一步没进。
下次请求又从头来一遍，形成死循环，白烧钱。

### 现在的做法

**每批成功就立刻落盘**（`store._flush_sync`）：

```sql
BEGIN IMMEDIATE;
UPDATE checkpoints SET summary = ?, compressed_upto = ?, round_upto = ? WHERE id = ?;
COMMIT;
```

摘要和压缩位置**必须在同一个事务里**。否则崩在两条语句中间会出现"下标推进了但摘要没写"，
那段原文就永久丢了。

- checkpoint 带 `partial` / `sealed` 状态，压缩事件全部完成才封存并开新的。
- 进程重启或中途失败后，下次请求读到 `partial` 记录**接着压**（`store.resume_event` 会先把
  这条记录的坐标系刷新到本次请求的消息列表上，因为期间消息可能已经增删过）。
- **单次请求的批次上限** `max_batches_per_request`：压不完就带着已落盘的进度返回，
  避免单个 HTTP 请求跑几十分钟。**把一个几十批的长任务拆成多次请求渐进完成，
  这是终结死循环的关键。**

重试时不会因为用户改了最后一句就判成新分支：对齐只要求 `matched_ref >= compressed_upto`，
而 `compressed_upto` 远在报错轮次之前。

### 摘要模型的重试分类（`summarizer.call_chain`）

| 错误类型 | 处理 |
|---|---|
| 超时 / 5xx / 429 | 指数退避重试，429 优先读 `Retry-After` |
| `context_length_exceeded` | **不重试**，把输入二分后重投（重试同样的输入没有意义） |
| 401 / 403 / 402 / 余额不足 | **立即失败**，错误信息里点明是鉴权还是余额，不做无差别重试 |
| 输出 < `min_output_tokens`（默认 50，**不含思考部分**） | 判定为失败，重试 / 切备用 |

主模型耗尽 `main_max_attempts` 后切 `fallback`，fallback 最多 3 次，仍失败则报错结束，
**已落盘的部分全部保留**。

### 二次重压和批次摘要同构

累积摘要超过 `summary_total_cap_tokens` 时触发二次重压。做法和批次摘要**完全一样**：
按 `summary_batch_tokens` 切片 → 每片用同一套 `prompts.recompress` 调一次 →
**系统用空行拼接**。结果写成新的 checkpoint，不覆盖旧的（旧的留着回退）。

早先这里是两段式：分片阶段用一套"禁止输出章节标题"的提示词精简，最后再调一次模型
把片段合并成唯一一套章节。动机是怕多片各自生成一整套章节、合并后出现 N 份重复章节。
实际用下来太零散——多一次调用、多一套提示词、多一层失败面，产出还不见得更好，
而且普通压缩本来就是"每批各自成文 + 系统拼接"，两条路径不一致反而难解释。
现在统一成一套，重复章节交给提示词自己约束（"沿用已有章节，不要新增"）。

### 提示词：整条 user 消息，用户能改的就是发出去的

提示词一共四套（批次摘要 / 二次重压 / 注入主模型的包装语 / 兜底警告语），
在 `config.yaml` 的 `summary.prompts` 下，也能在 `/ui` 的「提示词」页直接改。

发给摘要模型的那两套（`batch` / `recompress`）是**整条 user 消息的模板**，
`{{context}}` 处插入待处理的正文：

```
（你写的提示词）

以下是待压片段
{{context}}
```

早先是 system 放提示词、user 放一段硬编码的包装语（"请把下面这段对话片段压缩成…
=== 对话片段开始 ==="）。问题是那段包装语用户改不到，页面上看到的和实际发出去的对不上；
而且 system/user 怎么分本身就是代理替用户做的决定。现在整条走 user，
模板即所见即所发，要加分隔符、要换语气、要把指令挪到正文后面，都由用户自己决定。

`{{context}}` 是必填的：缺了它模型就只收到一句指令、正文整个丢掉，所以保存时会拦下来。
旧配置里的 `batch_system`（没有占位符）会自动迁移成 `batch` 并补上标准尾巴。

**页面上保存直接写回 `config.yaml`。** 早先是存数据库当覆盖项、不碰文件，
理由是整份 `yaml.safe_dump` 重写会把注释冲掉——但那样改完还得记着同步文件，
重启前后行为不一致。现在改成按行定位 `    <name>: |` 的块、只替换那段缩进正文，
文件的注释和排版一字不动；写之前 `config.yaml.bak` 备份一份，写的时候先解析校验、
再原子替换（写坏了宁可抛异常也不毁配置）。只有写文件失败时才退回内存覆盖项，
并在页面上明说"重启会丢"。

## 3. 绝不把未压缩的上下文放行到上游

旧版有多处压缩失败后 `return messages` 原样转发的降级路径。压缩服务的意义就是控成本，
降级成全量转发等于失去意义——一次几十万 token 的请求就是账单事故。

现在：

- 低于 `trigger_tokens` 的原样转发**保留**（短对话、只有 system 消息、无新增内容需压缩这几条路径，
  否则新对话全废）。
- 超过阈值而压缩没成功完成 → **报错**。
- 比逐条堵降级路径更可靠的是一道**出口闸门**（`compress._finish`）：转发前实测
  `count_tokens(final_messages)`，超过 `trigger_tokens × exit_gate_ratio`（默认 1.2）直接拒绝。
  这能捕获所有导致超标的原因，包括还没想到的 bug 路径。

错误是可行动的，直接写给用户看：

```
⚠️ 上下文压缩未完成，本次请求已被代理拦截（不会按全量 token 转发给上游）。
原因：摘要模型调用失败（server）：…
进度：已压缩到第 52/93 轮（消息下标 104），剩余 41 轮 / 约 33900 tokens
已完成的部分已经保存，直接重发这条消息即可从断点继续，不会重复计费。
```

- **非流式**：HTTP 503 + 上述结构（`error.detail` 里有机器可读的字段）。
- **流式**：压缩阶段已经往 think 区吐过内容了，不能再返 HTTP 4xx，
  所以以 SSE 事件返回同样的文本 + `[DONE]`。

## 3.5 近期原文的硬性下限

`keep_recent_tokens` 不是"压缩时的一个参考值"，而是**贯穿所有路径的硬下限**：
只要这个会话触发过压缩，之后任何一次转发给上游的逐字原文都不得低于它
（除非整个对话本身就没这么长）。

压缩路径本身天然满足——`_pick_keep_from()` 就是按这个下限挑的切点。
问题出在**不压缩的那几条路径**上：它们直接拿 checkpoint 里的 `compressed_upto`
当原文起点，而这个存量位置在三种情况下会不再满足下限：

| 情况 | 后果 |
|---|---|
| 用户删掉了近期若干轮 | `compressed_upto` 一下子逼近消息列表末尾，原文只剩几条 |
| 运行中调大了 `keep_recent_tokens` | 存量 checkpoint 的切点是按旧值定的，天然偏小 |
| 旧库迁移来的 `compressed_upto` | 出自另一套阈值，与当前配置无关 |

这三种情况下等效总量都很小，会走"复用摘要"分支直接转发，模型于是只剩一点点原文
——**记忆精度断崖式下降，而日志上看不出任何异常**。

修法是把两个概念拆开：

* `compressed_upto`（checkpoint 状态）——决定「还有什么需要摘要」，**只前进不后退**；
* `retain_from`（本次请求的展示窗口）——决定「原文从哪条开始发」，
  由 `_floor_retain()` 算出，等于 `min(compressed_upto, 下限对应的轮边界)`。

`_floor_retain()` **只回退、不前推**，所以绝不会把尚未摘要的内容吞掉。回退的代价是
那几轮同时出现在摘要和原文里——重叠是无害的（注入提示词里明确以原文为准），
而原文不足是有害的。等下一次真正触发压缩时切点重算，重叠自动消失，属于自愈。

回退会打 `WARNING` 并写明是哪种原因。阈值判断（是否触发压缩）也改用 `retain_from`
之后的 token 量，保证"判断依据"和"实际发出去的内容"是同一个东西。

### 下限自身要封顶

下限是"保不住就报错"的硬指标，那它就不能大到和触发阈值打架：`keep_recent` 一旦逼近
`trigger`，压完一次剩不下多少余量，很快又触发，叠上摘要还会顶穿出口闸门。

所以有效值在 `config.keep_recent_tokens()` 里**自动封顶为 `trigger_tokens × 50%`**
（常量 `config.KEEP_RECENT_MAX_RATIO`）：配置写小于这个数就按配置来，写大了一律按
`0.5 × trigger` 生效，并在加载配置时打一次 `WARNING`。代码里一律走这个函数，
不要直接读 `summary()["keep_recent_tokens"]`。`/health` 同时暴露配置值和有效值。

封顶之后，"下限 + 摘要"在正常配置下不可能顶穿 `1.2 × trigger`，
出口闸门的拦截就只剩两种真实成因，`_finish()` 会分开归因：

| `cause` | 含义 | 给用户的建议 |
|---|---|---|
| `batch_cap` | 本次请求到了 `max_batches_per_request` 上限，还没压完 | 重发几次即可，进度已落盘 |
| `oversize_tail` | 压无可压——最后一轮原文自己就顶穿了闸门 | 编辑/缩短最后一条消息后重发，别在这一轮让模型调用工具 |

`oversize_tail` 时错误信息里会报出最后一轮的 token 数，以及**其中有多少来自工具调用与
工具返回**（`messages.tool_tokens()`，只用于归因，不参与任何阈值计算）。
工具调用的请求与结果会整段留在近期原文里、压缩碰不到，是这条路径最常见的成因。

`_finish()` 里另有一句告警型自检：还有原文可留却留少了就打 `ERROR`，抓漏网的 bug 路径。

## 3.55 「压缩中」和「没压完」不是一回事

用户报的现象：明明没有任何请求在跑，页面却一直显示"摘要压缩中、无法编辑"。

根因是拿 checkpoint 的 `partial` 状态当"正在压缩"。但 `partial` 恰恰是本设计里
**最正常的静止状态**——逐批落盘 + 下次请求接着压，意味着这些情况都会留下 `partial`
并停在那里：

- 单请求批次上限 `max_batches_per_request` 没压完（设计如此）；
- 摘要模型报错、中转站返回错误页、出口闸门拦截（进度已落盘）；
- 进程重启、客户端断连。

它可以停留几天，直到用户下次发消息才被推进。把它读成"压缩中"，就等于说
"只要上次没压完，就永远不许改摘要"——而想改摘要的人，多半正是因为上次没压好。

真正的"正在压缩"只有进程自己知道：`prepare()` 持锁期间往 `_INFLIGHT` 登记，
走完就销号。于是：

| 概念 | 数据来源 | 用途 |
|---|---|---|
| 正在压缩 | 进程内 `_INFLIGHT`（`/health` 的 `compressing_now`） | 决定摘要能不能改 |
| 没压完 | DB 里的 `partial`（`/health` 的 `unfinished_compressions`） | 提示"下次请求会接着压" |

编辑摘要不再看 `partial`，只看有没有请求在跑——而且判断方式就是去抢同一把会话锁，
抢到了就说明没人在压。保存时顺带把这些半成品标成 `stale`（见下）。

## 3.6 手工改写摘要与指定当前 checkpoint

摘要模型压出来的东西不理想时，可以直接改（`./ctl.sh edit <id>`，或 `PUT
/admin/session/{id}/summary`）。实现上刻意复用了已有的 checkpoint 模型，没有另开机制：

* 改动写成一条 **`kind='manual'` 的新 checkpoint**，位置信息（`compressed_upto` /
  `round_upto` / `signature`）整套从被编辑的那条 SQL 层面复制过来——用户只改了摘要文字，
  历史对齐关系没有变。原 checkpoint 留在链上，改坏了照常能回退。
* 因为 `choose_checkpoint()` 是按 `seq` 倒序挑第一个可用的，新写的 manual 自然接管；
  下一次压缩事件以它为基线往后追加，所以手写内容不会被覆盖。

三道保护，都是这个架构里已经存在的风险点：

三道保护，都是这个架构里已经存在的风险点：

| 风险 | 保护 |
|---|---|
| 和正在跑的压缩交错写 | 管理接口拿的是**同一把会话锁**（`compress.conversation_lock()`），抢到锁就说明没人在压 |
| 取回之后又压了一次，写回把新内容盖掉 | `base_seq` 乐观锁，seq 对不上就 409 |
| 手写内容超过 `summary_total_cap_tokens` | 拒绝保存——否则下次压缩会触发二次重压，把人写的东西洗成模型的话 |

锁这里有个细节：`prepare()` 是在知道 `conv_id` 之前就要上锁的（上锁才能安全地查会话），
所以锁键用的是 `conv_key`；管理接口只有 `conv_id`，从会话表回查 `conv_key` 才能拿到同一把锁。

### 「设为当前摘要」：让它真的长期生效

`POST /admin/session/{id}/checkpoint/{seq}/activate` 把链上任意一条 checkpoint
指定成当前生效的摘要。做法同样是复制一条新的 manual 放到链首，而不是删掉后来的——
更晚的照样留着，选错了能再选回去。

要让"以后都用它"这句话成立，光有最大的 `seq` 不够，还得堵住两条会绕过它的路：

1. **未压完的半成品会把它绕过去。** `partial` 的 `seq` 比新指定的这条小，
   但续压走的是 `open_event_checkpoint()`（专挑 `partial`），会在**那条**的摘要上继续追加。
   下次请求一来，实际生效的就又变回系统压的内容了——用户描述的"重启后又变回去"就是这条路径。
   所以指定当前时把该会话所有 `partial` 标成 `stale`：不再被续压，但记录留着可查。
2. **裁剪会把它删掉。** `_prune()` 只保留 `pinned` 的和最近 `keep` 个事件。
   手工指定的这条标成 `pinned=2`（`1` 是永久置顶的最早那条），永远不裁；
   每个会话只保留最新的一条手工置顶，指定新的时候把旧的降回 `0`。

编辑摘要保存走的是同一条路径（`pin=True`），所以"改完就是当前、重启还是它"是默认行为，
不需要用户再点一次。

## 3.7 请求快照（时间轴）与性能账

页面上的「进来 → 发出去」对比和对话时间轴，数据来自每次请求存的一份**结构快照**。

**明确不存完整原文，只存每轮开头 `preview_chars` 字（默认 60）的预览。**
存完整 payload 意味着每次请求写几十 MB——小机器的磁盘和 IO 都扛不住，
而且那是用户对话的完整副本，落盘本身就是隐私风险。快照里每一轮只有：
轮号、消息下标区间、token 数、角色序列、首条 user 消息的前 `preview_chars` 字预览、
以及**这一轮是被折叠进摘要还是逐字发出**。所以时间轴能回答"哪条之前的内容被压掉了"，
但不能回放整轮内容——要看完整原文去 chatbox 里看，那才是原文该待的地方。

预览是逐字截取的真实片段，不做任何脱敏；把 `preview_chars` 调大就是把更多原文写进库。
换句话说快照降低的是**存储量**，不是敏感度——`sessions.db` 本来就存着摘要全文，
无论开不开时间轴，都该按"存放对话内容的库"来设权限。

实测（`observability.capture_timeline: true`）：

| 会话规模 | 构建快照 | 落盘 | 快照大小 |
|---|---|---|---|
| 500 轮 / 1000 条 | 1.5 ms | 1.3 ms | 116 KB |
| 2000 轮 / 4000 条 | 13.3 ms | 4.9 ms | 460 KB |

对照：一次真实请求光等上游就要几秒，所以最坏情况下这是 **0.3% 量级的开销**。
落盘走 `asyncio.to_thread`，不占事件循环；构建那 13 ms 是同步的，但只在开关打开时发生。
每个会话**只保留最新一份**（`timelines` 表主键就是 `conv_id`，覆盖写），
所以 DB 增量是「会话数 × 单份大小」而不是随请求数无限增长。

**默认关闭**（`capture_timeline: false`）。想用页面的时间轴就打开，
不看的时候关掉，一分钱开销都没有。

## 3.8 上游参数怎么过

**`messages` 之外一律不碰。** 转发就一句 `{**body, **extra_body, "messages": prepared.messages}`，
所以 `temperature` / `top_p` / `seed` / `tools` / `response_format` / 各家思考开关 /
厂商私有字段全都原样过去，将来出现的新参数也自动支持——不维护白名单，就不会漏。

三个配置项补上代理必须介入的部分：

| 配置 | 为什么需要 |
|---|---|
| `providers[].extra_body` | 强制客户端界面表达不了的参数（思考强度等）。**覆盖**客户端同名字段——这个配置的用途就是"我说了算"。`messages` / `stream` 在加载配置时就被剔除，改它们等于绕过压缩、破坏流式处理 |
| `providers[].forward_headers` | 请求头默认不透传。无脑转发会把 `cookie`、`x-forwarded-for` 一起漏给上游，所以按名字白名单放行。`authorization` / `host` / `content-length` 等永远拒绝——鉴权头必须换成供应商的 key，传输层的头由 httpx 重算 |
| `providers[].forward_query` | 查询串默认不透传；Azure OpenAI 的 `?api-version=` 需要它 |

摘要模型侧对应 `summary.extra_body`（`summary.fallback.extra_body` 不写就沿用主模型的）。
在 `summarizer._one_call` 里 extra_body 先铺底、再让 `model` / `max_tokens` / `messages` /
`stream` 覆盖它——那四个是这条调用链的骨架，不接受改写。

### 该往 extra_body 里写哪个字段名：`tools/probe_body.py`

思考开关的字段名各家不同，写错的失败模式还分两种：有的网关 400，有的默默丢掉。
后者尤其坑——你以为思考开了，其实一直没开，而且从对话里看不出来。

所以给了个探测脚本：一个字段发一次最小请求，最后打出「可用 / 被拒 / 无法判断」。

这类工具真正的难点不是发请求，而是**别给出错误的结论**——用户会照着结论删配置，
一条假的"被拒"比没有结论更贵。所以判定链上每一环都要求证据是充分的：

| 步骤 | 请求 | 判定 |
|---|---|---|
| 1 基线 | 不带任何探针字段 | 非 2xx → 中止（退出码 2）。问题在 key/模型名/base_url/余额，不在字段上 |
| 2 对照 | 一个瞎编的字段 | 400/422 **且报错文本匹配未知字段措辞** → 严格；2xx → 宽松；其余 → 无法判断（退出码 1） |
| 3 逐字段 | 每个候选字段 | 2xx → 可用；400/422 → 被拒；其余 → 无法判断 |

三处容易写错的地方：

- **"非 2xx 就是严格"是错的。** 401/429/5xx/网络错误说明的是*这次没问上去*，
  跟上游认不认这个字段无关。把限流读成"这家会校验未知字段"，
  会让后面每一条"可用"都被贴上一个它撑不起的保证。
- **"400 就是严格"也不够。** 400 也可能是余额不足、模型名不对。
  所以还要求报错文本命中 `UNKNOWN_FIELD_PAT`（覆盖 unknown/unrecognized/
  additional properties/未知/不支持 等常见措辞）；命中不了就把上游原文摆出来，
  让人自己判断，而不是替人猜。
- **没有基线，整份报告可能全是幻觉。** key 填错时每个字段都会"失败"，
  不做基线就会输出一份"所有字段都不可用"的清单，而真实结论是"你压根没连上"。

宽松网关下 `2xx` 只说明不报错，此时脚本退回间接信号：响应里的 `reasoning_content` /
`usage.completion_tokens_details.reasoning_tokens`，看开关的开与关能不能拉开差别。

其余几个细节：探针串行发而不是并发（并发容易自己撞限流）；429/5xx/网络错误会先自动
重试一次再判定；出现存疑项时回头复查一次基线——**如果基线这时也挂了，说明端点是中途
出的问题，整轮结果一起作废**（退出码降为 1），而不是留下一份半真半假的清单。
`--via-proxy` 走本地代理打上去，顺带验证 `extra_body` 与白名单请求头确实转发了出去。

### 流式平滑会重写正文分片的元数据

`stream.smooth_chars > 0` 时，被切片的正文 chunk 由代理重新打包，`id` 变成
`chatcmpl-proxy`、`system_fingerprint` 在这些分片上丢失（`reasoning_content` /
`finish_reason` / `usage` 都保留，正文能完整拼回）。**设 `smooth_chars: 0` 就是逐字节
原样透传**，也是最快的——平滑本来就是那个 `peer closed connection` 的元凶，
没有特别理由建议关掉。

## 3.9 两把钥匙的隔离

`auth_token` 要填进 chatbox，跟着**每一个**对话请求走：它在客户端配置里、在抓包里、
在任何一个能看到请求的地方。拿这样一个 token 兼作后台密码，等于把后台钥匙散出去。

所以 `_accepted_tokens()` 的规则是双向的：

| 接口 | 认哪个 |
|---|---|
| `/{provider}/v1/*` | 只认 `auth_token`。`ui_token` 调不动付费通道 |
| `/admin/*` | **配了 `ui_token` 就只认 `ui_token`**，`auth_token` 一并失效 |
| `/admin/*`（没配 `ui_token`） | 退回 `auth_token` |

最后一行是为了不把 `./ctl.sh` 逼死：没配 `ui_token` 时页面本来就是关的（`/ui` 直接 404），
后台只有本机 CLI 在用，此时唯一的 token 就该能用。配了之后 `ctl.sh` 自己改用 `ui_token`
（读 config.yaml，或环境变量 `PROXY_UI_TOKEN`）。

比对用 `hmac.compare_digest`，且先把所有候选都比完再看结果——`any()` 是短路的，
写成 `any(compare_digest(...) for ...)` 会让"第几个才匹配上"变成可测量的时间差。

## 4. 并发与性能

服务器是 2 核 4G 的轻量云主机，还要跑 1panel + 一个 chatbox + 一个 CPU-only 的 ollama，
所以事件循环里不能有长时间同步计算或阻塞 IO。

| 旧问题 | 现在 |
|---|---|
| **没有会话级锁**，两个请求同时从同一位置开始压，各调一次摘要模型再互相覆写 | `compress._lock_for()` 提供 per-conversation `asyncio.Lock`，「查会话 → 定位 → 压缩 → 落盘」全程持锁，顺带吃掉客户端的重复/重试请求。锁字典 LRU 清理防泄漏（正在持有的锁不会被淘汰） |
| **token 计数重复编码**：同一批消息被 tiktoken 编码 4–5 次（tail 求和、倒序循环、分批统计、每批日志、末尾总计） | `messages.analyze()` 一次算出每条消息的指纹 + token 数，全流程复用；文本 token 数按内容哈希缓存，**下一次请求只需要编码新增的那几条**。实测 4000 条 / 55 万 token：首次 282 ms，之后 30 ms |
| 大列表编码仍会占住事件循环 | 消息数 > 200 时 `analyze` 丢进 `asyncio.to_thread`（tiktoken 编码时释放 GIL） |
| **同步 sqlite3 跑在事件循环里** | `store.Store` 的所有 async 方法都包 `asyncio.to_thread`，连接开 WAL + `synchronous=NORMAL` + `busy_timeout` |
| **流式平滑过激**：每 2 字符切一片 + 每片 sleep 10ms，3000 字回复要发 1500 个事件、睡十几秒；上游生产快于下游消费，响应全堆内存，连接闲置超时（日志里的 `peer closed connection without sending complete message body`） | 上游读取放进独立任务全速消费，平滑只作用于吐出；**上游已结束**或**待发积压超过 `flush_backlog_chars`** 时丢弃剩余延迟，一次性拼接吐完。默认参数也从 2 字符/10ms 放宽到 24 字符/8ms |

关于"流式输出转圈、切页面后发现早就输出完了"：这个现象在本服务侧的可疑点是
上面的平滑积压 + `[DONE]` 收束。现在保证**任何退出路径都恰好发一次 `data: [DONE]`**
（包括上游报错、压缩拒绝、客户端断连），且不再人为拖慢。如果换一个 chatbox 仍能复现，
那基本可以确认是客户端侧的问题。

### 其他一并修掉的

- **`comp_task.result()`**（流式分支）：任务未完成时会抛 `InvalidStateError`；客户端断连产生的
  `CancelledError` 也没被 `except Exception` 接住，会从异步生成器里逃逸。
  现在改成 `await`，并单独 `except asyncio.CancelledError` 处理取消（取消压缩任务后原样上抛）。
- **`ctl.sh` 启动时用 `>` 截断日志**，每次重启抹掉上一次的崩溃现场——这是之前查不到崩溃原因的
  直接原因。现在进程自己用 append 模式 + 轮转写 `logs/proxy.log`，`ctl.sh` 也只 `>>` 到
  `logs/stderr.log`；另外装了 `sys.excepthook` / `threading.excepthook` /
  事件循环 exception handler，未捕获异常带完整 traceback 落盘。
- **token 估算漏算非文本内容**：`tool_calls`、图片一律算 0 token，导致等效总量系统性低估、该压时不压。
  现在图片按 `tokenizer.image_tokens`（默认 1100）估、`tool_call` 按序列化文本估；
  `msg_tokens` 和 `count_tokens` 口径统一（都含 `per_message_overhead` + role）。
- **`per_message_overhead` 在模块加载时读取**，热重载改不动。现在所有 tokenizer 参数都在
  调用时才取值，`reload` 立即生效（只有 `encoding` 仍需 restart）。

## 5. 三个开放问题的答案

### 摘要放在哪个角色下更不容易让模型感到困惑？

**`system`**（`summary.summary_role` 可改成 `user`）。

- 放 `assistant`：模型会把它当成"自己说过的话"，容易在回复里复读摘要内容、或者
  把摘要里的措辞当成自己的语气基线。
- 放 `user`：容易被当成新的指令来执行，尤其摘要里有"待办清单"章节时。
- 放 `system`：模型对 system 的预期就是"这是背景设定/记忆"，最贴近摘要的真实语义。
  注入模板里还显式说了「把它当作你自己的记忆，不要向用户提及摘要的存在」。

少数只允许一条 system 消息的上游可以把 `summary_role` 改成 `user`。

### 摘要和原文的顺序如何排列能最大可能性命中缓存？

固定为 **`[开头 system] + [摘要] + [近期原文]`**。

上游的 prefix cache 是**前缀**匹配的，只要开头一段字节完全一致就能命中。

- 摘要只在**压缩事件发生时**才变，中间可能几十轮都不变；
- 原文是**只增不改**的追加序列。

把摘要放在原文之前，请求的前缀在两次压缩之间完全稳定，中间所有轮次都能命中缓存；
反过来把摘要贴在最后一条消息旁边，每轮的前缀都会因为新消息插在摘要之前而变化，缓存必然失效。

代价是压缩事件发生的那一轮会整体 miss 一次——这没法避免，但频率远低于每轮 miss。

### 工具调用历史的最优处理方法

分三段处理：

1. **切分**：轮的定义保证 `assistant(tool_calls)` 和它的 `tool` 返回始终在同一轮内，
   压缩切点只落在轮边界，永远不会把它们拆开。
2. **进摘要时**：渲染成 `[调用工具 name(args)]` / `[工具返回] …` 的稳定占位文本
   （`messages.message_text`），提示词里明确告诉摘要模型这些是占位标记、按语义概括即可。
   工具调用的价值绝大多数在**结果**而不在调用形式，压成一句"查了 X，得到 Y"通常就够了。
3. **保留区**：原样透传。转发前再兜一道 `sanitize_for_upstream`，
   丢掉找不到对应 `tool_calls` 的孤儿 `tool` 消息（客户端截断历史时会产生，上游会直接 400）。

token 估算上，`tool_calls` 按序列化后的文本长度计入，不再算 0。

### 附：图片

- **指纹不计入图片的 URL / base64**，只留一个稳定占位符。某些 chatbox 删除云端文件后会把
  历史里的 base64 换成自家私有 id——如果计入指纹，整段历史会瞬间"假分叉"。
- 转发前净化：非多模态供应商（`multimodal: false`）把图片换成 `[图片]` 文本；
  多模态供应商则把**失效的引用**（既不是 `data:` 也不是 `http(s)`）换成 `[图片（原文件已失效）]`，
  这正是旧版"删了云端图片之后 API 报错"的直接修复。
- token 按 `tokenizer.image_tokens`（默认 1100）估。
